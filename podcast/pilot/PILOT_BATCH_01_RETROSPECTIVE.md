## 3. What worked

### One contract can serve different episode types
The same episode architecture successfully handled foundation, transition, standards-heavy and quantitative topics.

### Audience/stage framing works
DEV/LVP/SVP prevents a common failure: teaching a practice without saying when it becomes necessary. The prototype-shortcut + expiration pattern is especially valuable for Audience A.

### Listener tools make the series practical
The pilot produced reusable work products rather than vocabulary-only teaching: requirements sheet/check, prototype evidence transfer/expiration card, industrialization gap review, risk-to-control chain/quality-gate check, capacity reality/constraint hunt.

### Claim/evidence separation works
P0 claims can remain visibly unresolved without blocking structural episode design. Internal frameworks remain distinguishable from external standards and guidance.

### The frozen backbone survived the stress test
No pilot finding requires a new domain, changed global invariant or replacement of DEV/LVP/SVP.

## 4. Packaging repairs before scale

### Repair R1 — add Episode Type
Every pack shall identify one primary type:
`FOUNDATION / TRANSITION / PROCESS / QUALITY-STANDARDS / QUANTITATIVE / CASE / SYSTEMS-DATA / AUTOMATION-DECISION`.

Purpose: allow the template to make some sections conditional instead of forcing equal depth everywhere.

### Repair R2 — separate stable claims from evidence status
`CLAIM SET STABLE` means episode truth boundaries and claim inventory are stable. It does not mean evidence is verified.

Every pack header shall show both:
- `claim_set_status`
- `evidence_status`

### Repair R3 — add a compact Source Gate Summary
Every pack shall expose counts for:
- P0 claims;
- P0 verified;
- unresolved normative claims;
- quantitative claims needing independent check;
- case facts needing primary-source confirmation.

### Repair R4 — make navigation first-class
Every pack shall contain:
- season;
- primary listener route(s);
- `start_here_if`;
- prerequisites;
- 30–90 second recap requirement;
- next episode;
- optional deep dives/topic tracks.

This preserves the seven-season/navigation architecture and prevents the 68-episode map from behaving like a mandatory linear course.

### Repair R5 — control episode density
A research pack may be comprehensive; an episode should not attempt to narrate every claim.

Each pack shall identify:
- `core_on_air_claims` — normally 5–9;
- supporting claims for show notes/deep dives;
- material explicitly deferred to another episode.

### Repair R6 — add Standards Acquisition hook
If a pack depends on a controlled standard/manual, record:
- exact document needed;
- current possession status;
- edition/status verification;
- licensing note;
- whether absence blocks EVIDENCE VERIFIED.

### Repair R7 — quantitative audit artifact
Quantitative-heavy packs shall maintain a compact calculation table with formula, units, assumptions, result and independent-check status.

### Repair R8 — technical reviewer profile
Before TECHNICALLY REVIEWED, identify the reviewer competence needed (e.g. quality/core-tools, operations/IE, machine safety, electronics manufacturing), not merely a generic reviewer.

## 5. Template scaling rules

### Mandatory for every technical episode
1. metadata/navigation card;
2. episode promise and listener decision;
3. audience contract;
4. core claim register;
5. applicability/boundary statement;
6. worked example/case where useful;
7. actionable listener tool;
8. source gate summary;
9. unresolved research;
10. next-navigation.

### Conditional modules
- standards gate — standards/manual-heavy packs;
- quantitative audit — consequential calculations;
- case fact sheet — real-world cases;
- safety/regulatory gate — safety/regulatory claims;
- field-evidence loop — field reliability/complaints/CAPA;
- data/genealogy module — traceability/digital-thread topics.

## 6. Scale strategy

Do not open all remaining packs as one undifferentiated queue.

Use **season-based production waves**, with navigation preserved:

1. Wave S1 — Season 1 / founder and early-development foundation.
2. Wave S2 — prototype → manufacturable product transition.
3. Wave S3 — build the production system / NPI / process / capacity.
4. Wave S4 — quality, validation, reliability and evidence.
5. Wave S5 — suppliers, sourcing and industrialization network.
6. Wave S6 — automation, manufacturing systems, data and OT security.
7. Wave S7 — scale, economics, field learning and continuous industrial maturity.

Within each wave, prioritize episodes that unlock the greatest number of later prerequisites.
