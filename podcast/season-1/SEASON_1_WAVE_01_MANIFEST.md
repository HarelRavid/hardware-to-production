# Season 1 — Wave 01 Production Manifest

status: ACTIVE
season: Season 1 — Build the Right Thing
purpose: Open the first post-pilot production wave using the frozen Episode Research Pack Template V1 and listener-navigation architecture.

## Production rule
Every new or updated project artifact created in this wave is committed to GitHub as part of the work. No canonical production content remains chat-only.

## Wave objective
Convert the Opening Arc into stable research packs that give early hardware teams a practical path from idea to coordinated multidisciplinary development without front-loading factory bureaucracy.

## Wave 01 scope
This wave opens the remaining foundational Season 1 episodes around the already-stabilized pilot anchors A1 and A4.

- A4 — Choosing Prototype Technologies Without Trapping the Product — CLAIM SET STABLE

- A3 — System Architecture & Interfaces: Preventing Cross-Discipline Integration Failure

## Audience target
Primary: founders, early technical teams and first engineering hires.
Secondary: NPI/industrialization engineers joining an immature product program.

Lifecycle emphasis:
Idea → Requirements → Team/ownership → Architecture/interfaces → Prototype technology choice → serious discipline prototypes → verification/configuration.

## Navigation behavior
Season 1 is not a mandatory linear course.

Entry points:
- A1 for idea/requirements-stage teams.
- A3 for teams already facing integration/interface problems.
- A4 for teams already prototyping.
- A5/A6 for discipline-specific teams needing a more serious prototype.

Each episode must preserve standalone usability through short prerequisite recap rather than hidden dependencies.

## Wave-level listener promise
By the end of this wave, a small hardware team should be able to answer:
1. What are we actually trying to build and prove?
2. Which disciplines/owners are missing?
3. Which interfaces are likely to fail at integration?
4. Which prototype shortcuts are legitimate, and when do they expire?
5. What makes the next mechanical/electronics prototype more informative rather than merely prettier?

## Production gates
Each pack progresses through:
`RESEARCH PACK OPEN → CLAIM SET STABLE → EVIDENCE VERIFIED → TECHNICALLY REVIEWED → SCRIPT READY → PODCAST READY`

Wave 01 completion does not require scripts. It requires claim-set stability and explicit evidence backlog for each pack.

## Shared guardrails
- DEV/LVP/SVP are internal lifecycle lenses, not external standard labels.
- Do not imply every startup needs enterprise systems-engineering tooling.
- Do not treat component-level success as system-level proof.
- Do not treat prototype quantity as readiness evidence.
- Prototype shortcuts require explicit expiration triggers where relevant.
- Cross-discipline interfaces require ownership and verification intent.
- New external claims enter the Source Verification Backlog rather than being silently treated as established fact.

## Wave metrics
Track per episode:
- core claim count;
- P0/P1/P2 count;
- open P0 source items;
- worked examples;
- listener tools;
- prerequisites;
- recap burden;
- unresolved terminology/applicability issues.

- exposing a frozen-backbone contradiction;
- duplicating existing technical truth;
- requiring excessive prerequisite listening;
- losing the practical founder/early-team orientation.
